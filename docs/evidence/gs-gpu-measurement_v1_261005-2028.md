# GS Action — 실제 GPU 측정 결과 해석 (사용자 PC)

## 1. 측정 조건

| 항목 | 값 |
|---|---|
| GPU | AMD Radeon(TM) Graphics (내장), ANGLE/D3D11 |
| 브라우저 | Chrome 154 (Windows) |
| 화면 | 1920×922, DPR 1.25, 품질 auto, 프레임 제한 60, 주사율 145Hz ÷ 2 |
| 빌드 | 결과 텍스트에 `사전 관측 … 고정 목표` 줄이 있음 → **PR #3 계열 빌드(v35)**. main v34 코드에는 이 줄이 없음(확인함). 제목은 둘 다 "GS_Action v34". 파일 해시는 측정 텍스트에 없어 직접 확인 못 함 |
| 목표 | 설정 60이지만 145Hz ÷ 2 = **72.5 FPS**가 목표로 고정됨 |

예산(내부 기준, 목표 72.5 FPS): 평균 ≥ 68.9, p95 ≤ 16.6ms, p99 ≤ 27.6ms, 최대 ≤ 100ms. 세 번 모두 평균·p95·최대에서 미달이고 p99는 60초 측정에서 0.3~0.4ms 차로 미달입니다.

## 3. 해석

1. **FPS 자체는 문제가 아니었다.** 샌드박스(SwiftShader) 12~15 FPS는 환경 한계였고 폐기해야 합니다. 실제 GPU에서는 평균 약 66 FPS로, 사용자가 설정한 60 FPS를 넘습니다. 목표가 72.5인 이유는 설계상 145Hz를 2로 나누는 pacing 때문입니다. 즉 "예산 초과"는 설정 60이 아닌 72.5를 기준으로 한 판정입니다.
2. **문제는 평균이 아니라 꼬리(tail)다.** p95 21ms는 144.9Hz 기준 3 refresh(20.7ms)에 해당합니다. 프레임의 약 5% 이상이 vsync 한 칸을 놓친다는 뜻입니다. 여기에 100ms를 넘는 끊김이 60초에 4~5회, 최대 183~565ms가 있습니다. 체감 문제는 이쪽입니다.
3. **열 저하는 이 측정에서 보이지 않는다.** 10분 동안 첫 60초(62 FPS)보다 마지막 60초(65.1 FPS)가 낫고 p99도 개선됐습니다. 자동 조절이 해상도를 61%, FX 절감을 2단계까지 쓴 것이 원인일 수 있습니다. 10분 한 번, 이 기기 한 대의 결과입니다.
4. **draw call(최대 292~439)은 이 GPU에서 병목으로 보이지 않는다.** 따라서 D(폭풍 배칭)의 우선순위는 낮습니다. 단 이것을 직접 증명한 측정은 아닙니다.
5. **끊김의 원인은 아직 모른다.** 이 텍스트에는 끊긴 순간의 단계별 시간·호출 스택이 없습니다. v35의 JSON 결과에는 `phaseTotals`, `phaseSpans`, `longTasks`가 들어 있어 이를 보면 예열·VFX 생성·GC 등을 구분할 수 있습니다.

## 4. 추정과 사실의 구분

- 사실: 위 표의 수치, 이 빌드에만 있는 출력 줄, 145Hz÷2=72.5.
- 추정: "p95 = vsync 한 칸 놓침"(수치 일치로 보나 프레임 단위 확인은 안 함), 열 저하 없음, D 우선순위 낮음.
- 미확인: 어떤 빌드 파일로 측정했는지(해시), 노트북 전원/절전 상태, 브라우저 하드웨어 가속 외 설정, main v34와의 차이.

## 6. 결정이 필요한 것

예산 기준을 "설정 60"과 "pacing 목표 72.5" 중 무엇으로 볼지. 현재는 72.5입니다. 사용자의 의도(60 FPS 안정)에 맞추면 평균은 이미 달성이고 남은 과제는 p95 이하의 꼬리 지연입니다.
