# v34-runtime-8 잔여 작업 결과

## 변경

- 선택된 효과를 네 개씩 생성·컴파일한 뒤 예열한다. 한꺼번에 전부 렌더한
  후보는 한 번에 약 6초를 막아 철회했다. 네 개씩 나누는 후보에서는 준비가
  9.68초에서 7.28초로 줄었고, 가장 긴 예열 묶음은 약 2.5초였다.
- 화면 크기·픽셀 비율이 같으면 렌더 버퍼를 재설정하지 않는다. 달라지면
  크기와 비율을 한 번에 변경한다. 같은 비율의 compositor 재설정도 생략한다.
  세로 화면의 품질 제한은 기존대로 긴 변과 짧은 변 기준을 유지한다.
- 컨텍스트 손실은 미완료 모듈 준비를 취소하고 준비 캐시의 세대를 바꾼다.
  복구 뒤 새 준비를 시작하며, 이전 실패가 새 캐시를 지우지 못하게 한다.
  실제 시전·화면 전환의 기존 취소·렌더 타깃 복원은 유지한다.

GA_SIM·GA_SKILLS의 전체 스크립트와 스킬 수치는 초기 main에서 변경하지 않았다.

## 효과 전수 렌더

425개 스킬·767개 변형을 실제 Chromium/SwiftShader에서 렌더했다. 각 변형을
0.05초 간격으로 갱신하고 세 시각에 64×64 픽셀을 읽었다. 모든 변형에서 픽셀
변화가 있었고, 시전 거절·셰이더/GL 오류·비정상 좌표는 없었다. 네이티브 접촉
신호는 172건 수집했다. 신호가 없는 효과의 접촉 시각을 추정값으로 승인하지
않았다. 소리는 비활성화했으므로 청취 승인도 포함하지 않는다.

전수 검사 소스: `b40e56261a6dfdd00e48a2f2f7d945e9a83418c02bbcbd01fbc675b8b1643ab4`.
이후 모듈 준비의 컨텍스트 취소·캐시 세대 처리를 보완했다. 네이티브 효과의
생성·갱신·렌더 코드는 그 보완에서 변경하지 않았다.

재실행:

```bash
python3 scripts/audit_vfx_cloud.py --output cloud-results/vfx-all.json
python3 -m unittest discover -s tests -v
python3 scripts/benchmark_cloud.py --seconds 240 --cap 60 --loop --output cloud-results/repeat.json
```

렌더 전수 검사는 제어된 시간의 오류 검사다. 성능 측정은 별도의 실제 RAF
벤치마크를 사용한다. 두 검사를 동시에 실행하지 않는다. 벤치마크는 GPU 자원과
JS 힙 표본도 저장하며 `--quality auto|low|high`로 기존 품질 설정을 고를 수 있다.

## 성능 판단

같은 환경에서 다시 실행한 60초 기준 측정은 평균 15.4FPS·준비 9.68초,
네 개씩 예열한 후보는 평균 13.8FPS·준비 7.28초였다. 시작 대기는 줄었지만
전투 FPS 향상은 확인하지 못했다. 시각 효과 난수와 클라우드 실행 편차가 있으므로
한 쌍의 실행만으로 지속 성능의 원인을 확정하지 않는다. 프레임 목표는 낮추지 않았다.

전체 회귀 23개 통과. 복구 캐시 보완 후 실제 렌더 도구도 10개 스킬·32개 변형으로

최대 1127.7ms. 초반/후반 60초는 14.6/14.7FPS였다. 준비 실패·페이지 오류는 0건,
프레임 예산은 미충족이다. 같은 환경의 준비 기준 9.68초보다 약 23% 짧아졌다.

장면 루트 202개·파편 묶음 최대 58개를 유지했다. 이 관찰 범위에서 자원은
회수됐으며, 더 긴 실행이나 실제 기기의 누수·발열 승인으로 확대 해석하지 않는다.

GitHub API 접근은 환경 복구 후 정상화됐다. 이전 runtime-6 문서의 Forbidden은
당시 상태이며, 현재 변경은 초안 PR에서 검토한다.

## 부하 중 프레임 제한 보완

30FPS 제한이 느린 RAF도 두 번 중 한 번 건너뛰는 문제를 수정했다. 이제 경과
시간으로 다음 프레임을 결정한다. 이미 프레임 간격이 목표보다 길면 추가로
건너뛰지 않는다. 빠른 화면에서는 기존 주사율에 맞춘 제한을 유지한다. 측정
목표와 예산은 낮추지 않았다. `skipN`은 목표 주사율의 명목 분할 값이며 실제
부하 중 건너뛰는 RAF 수로 해석하지 않는다.

위 23개 회귀와 최종 240초 결과는 이 추가 수정 직전(runtime-7)의 검사다.
경과 시간 제한과 최종 runtime-8 검사는 아래 후속 결과에 구분해 기록한다.

## runtime-8 최종 검증
